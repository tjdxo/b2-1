# 나만의 용돈 기입장

Python **3.10+**, 표준 라이브러리만 사용하는 콘솔 가계부입니다. 별도 설치(`pip install`)는 필요하지 않습니다. 거래 내역을 파일로 보관하면서 조회, 수정, 검색, 통계를 처리하는 작은 콘솔 프로그램입니다.

## 실행 방법

압축을 해제한 프로젝트 루트(`pocket_budget/`)에서 실행합니다.

```bash
python -m budget_app --help
python -m budget_app add
python -m budget_app list --limit 10
```

저장 폴더 변경(전역 옵션은 **명령 앞**에 기입):

```bash
python -m budget_app --data-dir ./other_data list
```

명령 도움말: `python -m budget_app search --help` (모든 명령과 하위 명령에서 사용 가능)

## 설계와 폴더 구조

```text
pocket_budget/
├── README.md
├── .gitignore
├── budget_app/
│   ├── __init__.py      # 패키지 표시
│   ├── __main__.py      # python -m 진입점
│   ├── cli.py           # argparse, 사용자 입력, 출력, 예외 데코레이터
│   ├── models.py        # Transaction dataclass, 입력 검증, AppError
│   ├── storage.py       # JSONL 파일 입출력, 순차 읽기, 안전한 다시 쓰기
│   └── service.py       # 거래/카테고리/예산 규칙, 집계, CSV 변환
├── examples/
│   └── import_sample.csv
└── tests/
    └── test_budget.py
```

기본 저장 위치는 **프로젝트 실행 경로의 `./data/`**입니다. 첫 명령 실행 시 디렉터리 및 3개 파일이 자동 생성됩니다.

- `transactions.jsonl`: 한 행에 거래 JSON 객체 1개 (id, type, date, amount, category, memo, tags)
- `categories.jsonl`: 한 행에 `{"name":"food"}` 형태의 객체 1개. 파일이 비어 있으면 기본 `food, transport, rent, salary, etc` 생성
- `budgets.jsonl`: 한 행에 `{"month":"2026-10","amount":500000}` 형태의 객체 1개

JSONL은 UTF-8이고 데이터가 프로그램 종료 후에도 유지됩니다. `update/delete`는 임시 파일로 전체 재작성 후 교체하며, 이는 파일 저장 시 데이터 손실 위험을 줄이기 위한 **데이터를 안전하게 저장하기 위한 처리**입니다. 별도의 백업 명령은 제공하지 않습니다.

## 주요 명령

```bash
python -m budget_app add
# 프롬프트에 날짜, 타입, 카테고리, 금액, 메모, 태그 순서대로 입력
python -m budget_app list --limit 3
python -m budget_app search --from 2026-10-01 --to 2026-10-31 --category food --type expense --q 점심 --tag meal
python -m budget_app summary --month 2026-10 --top 3
python -m budget_app budget set --month 2026-10 --amount 500000
python -m budget_app budget get --month 2026-10
python -m budget_app category add
python -m budget_app category list
python -m budget_app category remove --name rent
python -m budget_app update --id TX-실제ID
python -m budget_app delete --id TX-실제ID
python -m budget_app import --from examples/import_sample.csv
python -m budget_app export --out october.csv --month 2026-10
python -m budget_app export --out range.csv --from 2026-10-01 --to 2026-10-31
```

`update`는 **대화형 고정**입니다. ID만 옵션으로 지정하고 모든 값을 순서대로 확인합니다. Enter면 기존 필드 유지, 메모/태그에 `-`를 넣으면 내용 삭제입니다. `category remove`는 사용 중이면 차단합니다. 예산은 월 총 **지출**과 비교하며 초과 시 경고를 출력합니다. 거래 날짜가 같으면 거래 ID를 보조 정렬 기준으로 사용합니다. ID는 무작위 고유 값이라 번호 순서가 곧 입력 순서는 아닙니다.

## CSV import/export 스키마

UTF-8, **헤더 포함**, 표준 CSV(쉼표 구분)입니다.

| 열 | 필수 | 설명 |
| --- | --- | --- |
| date | Y | YYYY-MM-DD |
| type | Y | `income` 또는 `expense` |
| category | Y | 등록된 카테고리 |
| amount | Y | 0보다 큰 정수 |
| memo | N | 문자열(없으면 빈 값) |
| tags | N | 태그 여러 개는 쉼표 구분. CSV 안에서는 `"meal,school"`처럼 큰따옴표로 감싸기 |

CSV에는 ID가 없습니다. **import 때 새 ID를 발급**하므로 동일 파일을 재가져오면 중복 내역이 생길 수 있습니다. 가져오기 전 CSV 모든 행의 유효성을 검증하고 한 행이라도 잘못되면 전체 가져오기를 취소합니다. 올바른 행은 전부 추가하며 `skipped=0`입니다. export는 필터를 필수로 받습니다.

## 구현하면서 정리한 내용

처음에는 거래 정보를 파일에 저장하고 다시 읽는 것만 생각했지만, 내용을 수정하거나 검색하는 기능을 붙이면서 **데이터 구조, 파일 접근, 사용자 명령을 구분할 필요**를 느꼈습니다. 그래서 프로그램을 크게 네 부분으로 나눴습니다.

### 데이터와 로직을 분리한 이유

`models.py`의 `Transaction`은 거래 한 건의 데이터 형태를 정의합니다. 날짜, 금액, 거래 유형처럼 거래 자체가 갖춰야 할 조건을 검증하는 역할도 맡습니다. `storage.py`의 `JsonlStore`는 그 데이터를 파일에서 읽고 쓰는 일을 담당합니다. 반면 `service.py`의 `BudgetService`는 카테고리가 실제로 등록되어 있는지, 월별 지출이 얼마인지, 카테고리를 삭제해도 되는지 같은 **가계부 규칙**을 처리합니다. `cli.py`는 사용자가 입력한 명령을 해석하고 결과를 보여줍니다.

예를 들어 월별 지출 합계 계산이 바뀐다면 `service.py`를 살펴보면 되고, JSONL 저장 방식을 변경한다면 주로 `storage.py`를 고치면 됩니다. 책임을 나누면 코드가 다소 길어지지만 수정해야 할 곳을 찾기는 쉬워집니다.

- `Transaction`: 거래 **한 건의 형태와 값 검증**
- `JsonlStore`: 거래 **파일을 어떻게 읽고 기록할지**
- `BudgetService`: 거래를 **어떤 기준으로 조회·수정·집계할지**

여기서 타입 힌트도 함께 사용했습니다. 예를 들어 `iter_transactions() -> Iterator[Transaction]`은 거래 객체가 하나씩 나온다는 것을 함수 선언만 보고 알 수 있게 해줍니다. IDE 자동완성이나 함수 간 연결을 이해할 때 도움이 되지만, 타입 힌트가 잘못된 사용자 입력을 자동으로 막아주지는 않아서 실제 날짜와 금액은 별도로 검증합니다.

### 저장 형식은 왜 JSONL로 정했을까?

거래 내역에는 숫자나 문자열뿐 아니라 여러 태그를 담는 `tags` 목록도 들어갑니다. CSV로도 저장할 수 있지만 이 경우 태그 목록을 쉼표로 합친 문자열로 바꿨다가 다시 해석해야 합니다. JSONL은 거래 하나를 JSON 객체 한 줄로 저장하므로 이 구조를 그대로 표현할 수 있습니다.

예를 들면 거래 파일에는 다음과 같은 줄이 들어갑니다.

```json
{"id":"TX-EXAMPLE","type":"expense","date":"2026-10-19","amount":15000,"category":"food","memo":"점심","tags":["meal","school"]}
```

또한 JSONL은 한 줄씩 읽을 수 있어 거래 파일 전체를 한 번에 불러올 필요가 없습니다. 다만 JSON 필드 이름이 매번 반복되어 파일이 커질 수 있고, 스프레드시트 프로그램에서 바로 다루기 불편하다는 단점도 있습니다. 그래서 **내부 저장은 JSONL**, 외부 데이터와 주고받는 **가져오기·내보내기는 CSV**로 나눴습니다.

실제 데이터는 `transactions.jsonl`, `categories.jsonl`, `budgets.jsonl`로 따로 저장합니다. 거래 내역을 지우거나 수정하더라도 예산과 카테고리를 별도로 보존하기 위한 구성입니다. 프로그램을 종료했다가 다시 실행해도 이 파일을 읽기 때문에 기존 내역을 이어서 사용할 수 있습니다.

### 거래가 많아졌을 때의 조회 방법

`storage.py`는 파일을 순차적으로 읽으면서 `yield`로 거래를 한 건씩 넘깁니다. `yield`는 모든 결과를 리스트에 담은 뒤 반환하는 것이 아니라, **필요할 때 다음 항목을 꺼낼 수 있게 하는 방식**입니다. 검색 조건을 만족하는 거래만 서비스 계층에서 다시 넘겨주도록 했습니다.

하지만 하나씩 읽는다고 해서 자동으로 최신순 정렬되는 것은 아닙니다. JSONL에는 거래가 입력된 순서대로 기록될 수 있기 때문입니다. 이 부분은 조회 유형에 따라 다르게 처리했습니다.

- `list --limit N`: `heapq.nlargest()`로 최신 N건만 유지합니다. 전체 거래를 모두 정렬하는 것보다 메모리를 적게 쓸 수 있습니다.
- `search`, `export`: 일정 개수(500건)씩 정렬해 임시 파일로 나눈 다음 `heapq.merge()`로 합칩니다. 전체 거래를 한 번에 메모리에 올리지 않고 최신순으로 출력하기 위한 방식입니다.

메모리 사용을 줄인 대신, 검색에서는 임시 파일을 만들고 읽는 **디스크 작업이 추가**됩니다. 예를 들어 거래가 10만 건이고 대부분이 검색 대상이라면 500건 단위 임시 파일이 약 200개 생길 수 있습니다. 거래 ID로 한 건을 찾거나 특정 달을 집계할 때도 현재는 파일을 순차 탐색합니다. 규모가 커지면 월별 파일 분리, 검색용 인덱스 또는 SQLite 같은 데이터베이스 사용을 고려할 수 있습니다. 현재 구현은 단일 사용자가 실행하는 파일 기반 프로그램을 전제로 합니다.

### 수정·삭제는 단순히 한 줄을 바꾸는 일이 아니었다

JSONL 파일은 데이터가 여러 줄로 이어지기 때문에, 한 거래의 내용이 길어지거나 짧아지면 파일 중간의 한 줄만 그대로 덮어쓰기 어렵습니다. 그래서 수정과 삭제는 다음 순서로 처리합니다.

1. 거래 ID가 존재하는지 확인합니다.
2. 기존 거래를 순차적으로 읽으면서 수정된 거래를 기록하거나, 삭제 대상은 건너뜁니다.
3. 결과를 원본이 아닌 **같은 폴더의 임시 파일**에 기록합니다.
4. 쓰기를 마친 다음 `os.replace()`로 원본 파일을 교체합니다.

원본을 읽는 도중 바로 덮어쓰는 것보다 안전하고, 교체 전 오류가 나면 기존 파일을 유지할 수 있습니다. 다만 이 방식도 동시 실행 프로세스 간 충돌까지 막는 것은 아닙니다. 여러 사람이 동시에 사용하는 서비스로 확장한다면 잠금이나 데이터베이스 트랜잭션이 필요합니다.

### 입력 오류와 CSV 가져오기를 처리한 방식

사용자가 날짜 형식을 틀리거나 음수 금액을 입력하면 저장하기 전에 검증하고 다시 입력하도록 합니다. 잘못된 거래 ID, 없는 파일, 잘못된 CSV처럼 명령 실행 중 공통으로 발생하는 오류는 `cli.py`의 `@handle_errors` 데코레이터에서 사용자에게 `[오류]`와 `[힌트]`를 표시하도록 모았습니다. 명령마다 비슷한 예외 처리 코드를 반복하지 않으면서 정상 종료와 오류 종료도 구분할 수 있습니다.

CSV 가져오기는 특히 **일부 데이터만 저장되는 상황**을 피하려고 했습니다. 파일을 순서대로 읽어 모든 행의 날짜, 유형, 카테고리, 금액을 검증한 뒤, 유효한 경우에만 기존 거래에 반영합니다. 잘못된 행이 발견되면 해당 행 번호와 오류를 알려주고 **전체 가져오기를 취소**하는 방식입니다. 일부 성공한 행을 별도로 정리해야 하는 혼란을 줄이기 위한 선택입니다. 반대로 이미 가져온 CSV를 다시 가져오면 새 ID로 중복 등록될 수 있으므로 사용자가 주의해야 합니다.

CSV는 UTF-8 헤더를 포함하며 `date,type,category,amount,memo,tags` 컬럼을 사용합니다. 여러 태그는 CSV 규칙에 맞게 따옴표로 감싼 하나의 필드로 표현합니다.

### 직접 확인한 실행 흐름

개발 과정에서는 데이터를 추가해 목록과 검색 결과에 나타나는지 확인하고, 거래 유형을 수정한 뒤 월별 수입·지출이 바뀌는지도 확인했습니다. 예산을 설정한 뒤 사용률을 출력했으며, 예제 CSV를 가져온 후 같은 달 거래를 내보냈을 때 파일의 내역과 건수가 일치하는 것도 확인했습니다.

자동 테스트는 Python 기본 `unittest`를 사용합니다. 거래 추가·수정·삭제, 카테고리 사용 조건, 검색과 예산, 잘못된 CSV의 가져오기 취소, CLI 오류 종료 코드 등을 다룹니다.

```bash
python -m unittest discover -s tests -v
```

테스트 5개가 통과하더라도 모든 입력 조합이 검증된 것은 아닙니다. 특히 손상된 저장 파일, 예산 초과 경고, 재실행 후 파일 유지처럼 실제 사용 환경에서 문제가 생길 수 있는 경우는 필요할 때 따로 확인하는 것이 좋겠습니다.

macOS/Linux에서는 오류가 발생한 명령 바로 다음에 `echo $?`를 실행해 종료 코드를 볼 수 있습니다.

```bash
python -m budget_app delete --id NOT-FOUND
echo $?
```

성공은 `0`, 처리된 명령 오류는 `1`로 구분하도록 구성했습니다.

### 현재 구조에서 더 생각해 볼 점

지금 프로그램은 개인이 터미널에서 실행하는 정도의 규모를 기준으로 만들었습니다. 그래서 별도 서버나 데이터베이스가 없고 실행과 저장 방식이 비교적 단순합니다. 반면 거래 파일이 아주 커지면 집계와 수정에 시간이 걸리고, 동일한 CSV의 재가져오기는 중복을 만들 수 있습니다. 파일이 손상되었을 때 오류를 정확히 알려주는 검증 역시 중요합니다. 이런 부분은 기능을 더 많이 추가하기보다, 사용하면서 데이터가 어떤 방식으로 안전하게 관리되는지를 이해하는 과정이라고 생각합니다.

## 데이터 초기화

처음 상태로 다시 실행하려면 프로젝트 폴더에서 기존 `data/`를 다른 이름으로 옮겨 백업할 수 있습니다.

```bash
mv data "data_backup_$(date +%Y%m%d_%H%M%S)"
```
